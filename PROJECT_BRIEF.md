# Проект ВКР: веб-сервис для выбора междугородних маршрутов при покупке железнодорожных билетов

Документ для работы с LLM (Claude Code и др.). Фиксирует всё, к чему пришли при выборе темы и первичной разведке. Дата составления: 14.11.2026. Разведка источников выполнена 08.11.2026, адреса запросов и вёрстка могут измениться.

## 1. Контекст

- Выпускная квалификационная работа бакалавра, ВолгГТУ, направление 09.03.03 «Прикладная информатика», кафедра «Информационные системы в экономике».
- Нужна только **техническая часть**: работающий продукт (сайт). Текст пояснительной записки пишется отдельно.
- Ориентиры по объёму и составу (по прошлым работам): Python + Django, около 8 моделей БД, пользовательский интерфейс, административная панель, развёртывание на сервере с доменом, тестирование. Такие работы занимают около 75-80 страниц и 30-40 рисунков.

## 2. Тема

**«Разработка веб-сервиса для выбора междугородних маршрутов при покупке железнодорожных билетов»**

Как понимаем тему в проекте: пользователь выбирает поезд на междугороднем маршруте, а сервис собирает предложения с нескольких площадок продажи билетов и показывает их рядом, чтобы выбрать лучший вариант по цене, времени и классу вагона. Поэтому в основе продукта сравнение цен одного и того же поезда на разных площадках.

- Объект исследования: процесс выбора и приобретения железнодорожных билетов через онлайн-площадки.
- Предмет исследования: разработка веб-сервиса сравнения предложений на основе Django.

## 3. Проблема и идея

- Железнодорожные билеты продаются на множестве площадок (РЖД, Туту, Яндекс Путешествия, Ozon Travel, УФС, Sravni и др.).
- Тариф на поезд один, но посредники добавляют сервисные сборы, дают промокоды, кешбэк и допуслуги, поэтому итоговая цена отличается. По наблюдениям автора, разница может доходить до 10-15% и более. Точных публичных цифр по сборам найти не удалось, их нужно замерить самостоятельно (для главы про анализ предметной области).
- Прямого сервиса «одна и та же поездка у всех продавцов рядом» найти не удалось (поиск был неглубокий, стоит перепроверить). Ближайшие найденные: БилетыПлюс (мультитранспортный агрегатор, список ЖД-источников не раскрыт). Туту, Яндекс, Ozon и УФС это продавцы, а не сравниватели.
- Идея: сервис собирает цены, нормализует их к единому виду и показывает сравнение, плюс историю цен.

## 4. Принятые решения (базовый вариант)

1. **Стек:** Python, Django, PostgreSQL (на разработке допустим SQLite), Playwright для сбора данных. Интерфейс на серверных шаблонах Django, графики через Chart.js. Язык интерфейса: русский.
2. **Два источника для начала:** Туту и Ozon Travel. Архитектура адаптеров должна позволять добавить новый источник без правок остального кода.
3. **Сбор данных отдельно от сайта.** Парсер запускается по расписанию на компьютере автора (домашний IP), результаты записываются в БД, сайт только читает из БД. Это снимает проблемы блокировок по IP и прокси на сервере. По умолчанию без Celery: расписание задаёт cron или Планировщик задач.
4. **Фиксированный набор маршрутов.** Например, 10-15 популярных направлений из Волгограда и горизонт 2-4 недели. Живого поиска по любому запросу нет, он остаётся в перспективах развития.
5. **Публичный запуск** на сервере с доменом, как в предыдущих работах.
6. **Вне объёма диплома:** платные оповещения о снижении цены, оплата, личные кабинеты с подписками, покупка билетов внутри сервиса. Это возможное развитие после защиты.

## 5. Разведка источников (08.11.2026, браузер на компьютере автора)

### Туту: подходит
- Сайт на Next.js. Адрес выдачи: `https://www.tutu.ru/poezda/Moskva/Sankt-Peterburg/?date=20.11.2026&travelers=1` (города в латинской транслитерации, дата в формате ДД.ММ.ГГГГ).
- Предложения приходят в страницу через WebSocket (`offers-api.tutu.ru`, адрес указан в `__NEXT_DATA__`). Готовая страница содержит всё нужное: номер поезда, время отправления и прибытия, вокзалы, время в пути, типы вагонов, число свободных мест, цены «от» по классам, иногда зачёркнутую старую цену и кешбэк.
- Отдельные эндпоинты: `vid-api.tutu.ru/api/calendar_prices` (календарь минимальных цен), `www.tutu.ru/poezda/vkz/api/timetable` (табло вокзала).
- Капчи при разведке не было.
- Нюансы: в выдаче есть рекламные блоки и баннеры, их надо отбрасывать. Скидки по картам и акции могут влиять на показанную цену. Выдача подгружается не сразу, нужно ждать появления карточек.
- Форма поиска капризная, проще открывать адрес выдачи напрямую.

### Ozon Travel: подходит с оговорками
- Адрес маршрута: `https://www.ozon.ru/travel/railway/volgograd-177578000/moskva-140158000/` (внутренние числовые ID городов). Сайт на Nuxt.
- Первая загрузка может показать антибот-страницу «Antibot Challenge Page» (HTTP 403), но это автоматическая JS-проверка, она проходится сама за несколько секунд. Парсер должен уметь ждать и повторять загрузку. При большом количестве запросов проверка может ужесточиться.
- На странице: список поездов с номерами, временем, вокзалами, ценами «от» по классам вагонов, ближайшими датами отправления и календарём цен.
- **Не проверено до конца:** цены на конкретную дату. Список маршрута показывает цены «от» без привязки к дате, а выбор даты ведёт в форму поиска. Эту часть нужно изучить при написании адаптера.

### Яндекс Путешествия: заблокирован
- Адрес выдачи: `https://travel.yandex.ru/trains/volgograd--moscow/?adult_seats=1&when=2026-11-20`.
- Сразу после первого открытия показывает Yandex SmartCaptcha («запросы похожи на автоматические»). Капчи не обходим и не решаем. Что за ней, неизвестно.
- Решение: в базовый вариант не входит. Возможная замена из списка автора: УФС (`ufs-online.ru`), Sravni (`sravni.ru/booking-rw`). Они не исследованы.

## 6. Предлагаемая архитектура

```
[Планировщик на ПК автора]
        │ запускает
        ▼
[Коллектор: Playwright + адаптеры источников]  --->  нормализация  --->  [PostgreSQL]
                                                                              ▲
                                                                              │ читает
                                                              [Django: сайт + админ-панель]
```

- Единый интерфейс адаптера, например: `fetch(route, date) -> list[RawOffer]`. Каждый источник реализует его отдельно.
- Нормализация: приведение номера поезда к единому виду (учитывать суффиксы и буквы, например «089Ж»), классов вагонов к четырём (сидячий, плацкарт, купе, СВ), цены к рублям за одного пассажира, времени к единой временной зоне.
- Сопоставление предложений разных площадок: ключ «номер поезда + дата отправления + класс вагона».
- Запись результатов в БД через команду Django (`manage.py`) или защищённый эндпоинт с токеном. Данные в виде снимков: каждый запуск добавляет записи, ничего не перезаписывает (так копится история цен).
- Сохранять сырые образцы ответов или страниц источников как фикстуры для тестов.

## 7. Черновик модели данных (около 8 моделей)

| Модель | Назначение |
|---|---|
| City / Station | города и вокзалы, внешние ID у источников |
| Source | площадка (Туту, Ozon), базовый URL, признак активности |
| Route | отслеживаемое направление (откуда, куда) |
| Trip | конкретный рейс: номер поезда, дата и время отправления и прибытия, время в пути |
| PriceSnapshot | снимок цены: рейс, источник, класс вагона, цена, число мест, время сбора, ссылка на страницу площадки |
| CollectionRun | запуск сбора: источник, начало и конец, статус, количество записей, ошибка |
| User / Favorite | (опционально) пользователь и избранные маршруты |

Модель предварительная, окончательную структуру определяет разработка.

## 8. Функциональность

**Пользователь (без регистрации в базовом варианте):**
- выбор направления и даты из доступных;
- сводная таблица предложений: поезд, время, вокзалы, время в пути, класс вагона, цена на каждой площадке, минимальная цена, разница в рублях и процентах, переход на площадку;
- сортировка и фильтры: цена, время отправления, время в пути, класс вагона;
- график истории цены выбранного рейса.

**Администратор (Django admin с доработками):**
- управление маршрутами и источниками;
- просмотр запусков сбора, статусов и ошибок;
- ручной запуск сбора, просмотр и правка данных.

## 9. Риски и ограничения

- **Данные.** Открытого API с ценами у источников нет, используется сбор общедоступных страниц. Вёрстка и адреса запросов меняются, поэтому адаптеры потребуют сопровождения.
- **Антибот.** Ozon проверяет JS-челленджем, Яндекс показывает капчу. Правила: капчи не обходить, запросы делать редко и с паузами, кэшировать, не создавать лишней нагрузки на чужие сайты.
- **Правовая сторона** (для публичного и коммерческого запуска): пользовательские соглашения источников, права на базы данных, закон о персональных данных при сборе контактов. Юридически не проверялось, перед монетизацией проверить отдельно.
- **Сопоставление.** Разные площадки по-разному показывают цену (с сервисным сбором, без него, «от» по классу), нужно сравнивать одинаковые условия и явно подписывать, что показано.
- **Запуск на сервере.** С адресов дата-центров блокировки жёстче, поэтому сбор вынесен на компьютер автора.

## 10. Что делает человек, а что LLM

**LLM (Claude Code) делает самостоятельно:** проект Django, модели, адаптеры, нормализацию, страницы и админку, тесты на фикстурах, Docker и конфигурацию развёртывания.

**Требует автора:**
- запуск Claude Code **локально** на компьютере автора, чтобы был доступ к живым сайтам;
- итерации «запустил парсер, посмотрел результат, поправил» и сверка цен вручную на нескольких маршрутах;
- решение по третьему источнику вместо Яндекса;
- сервер, домен, пароли и ключи (в чат и репозиторий не класть);
- периодическая правка адаптеров при изменении сайтов.

## 11. Порядок работ

1. Каркас проекта Django, настройки, модели, админка.
2. Адаптер Туту, тесты на фикстурах, запись в БД.
3. Нормализация и страница сравнения (пока с одним источником).
4. Адаптер Ozon, изучение цен на конкретную дату, сопоставление с Туту.
5. История цен и график, фильтры и сортировка.
6. Планировщик сбора, журнал запусков в админке.
7. Развёртывание: сервер, домен, HTTPS.
8. Тестирование (функциональное, сверка цен с площадками), скриншоты для пояснительной записки.

## 14. Правила работы с LLM

- Сначала прочитать этот документ целиком, затем предлагать план, затем реализовывать по этапам из раздела 11.
- Не обходить и не решать капчи, не использовать чужие аккаунты и данные пользователей.
- Не хранить секреты в коде и репозитории, использовать переменные окружения.
- Каждый адаптер сопровождать тестами на сохранённых образцах ответов.
- Любые допущения по данным источников явно помечать, непроверенное не выдавать за факт.
- Код и комментарии на русском или английском по согласованию, интерфейс сайта на русском.
